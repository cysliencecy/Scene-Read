# 决策记录

## 2026-07-15：第一版必须是手机 App

决策：产品形态从一开始按手机 App 定义，不再以网页 HTML 原型作为目标形态。

理由：用户明确要求技术选型和产品方向必须面向 App。

## 2026-07-15：第一版采用设计稿确认后的可体验 App

决策：原型初步满意后，下一步进入可运行 App，而不是继续扩展静态界面稿。

理由：需要开始验证真实移动端流程和技术可行性。

## 2026-07-15：跨平台优先

决策：第一版同时考虑 iOS 和 Android。

理由：避免一开始绑定单端，技术选型以跨平台为主。

## 2026-07-15：采用 React Native

决策：移动端框架选择 React Native。

理由：适合快速实现 iOS + Android，可与 TypeScript / Node.js 后端保持同一语言栈，利于快速迭代。

## 2026-07-15：采用 Expo Dev Client

决策：React Native 项目形态选择 Expo Dev Client。

理由：比 Expo Managed 更有原生扩展空间，比 React Native CLI 更适合第一版快速启动。

## 2026-07-15：采用混合执行架构

决策：App 本地负责导入、阅读、缓存；云端负责 AI 场景识别、生图和图片存储。

理由：全部云端隐私和等待成本较重，全部本地第一版复杂度过高。

## 2026-07-15：后端采用 Node.js API + Python Worker

决策：Node.js / TypeScript 负责业务 API，Python Worker 负责文本解析和 AI 任务。

理由：业务接口和 App 同语言栈更顺；AI、文本处理和 EPUB 解析用 Python 更方便。

## 2026-07-15：数据与文件选择 Supabase

决策：第一版使用 Supabase Postgres 和 Supabase Storage。

理由：书籍、章节、任务、图片天然适合关系型数据；Supabase 能减少第一版基础设施搭建成本。

## 2026-07-15：网上书籍检索走云端统一处理

决策：后续网上书籍检索导入由云端处理，不让 App 直接抓取书源。

理由：便于控制版权、授权、格式标准化、缓存和后续书源扩展。
